# Contributing to Tessera

Thanks for your interest. Tessera is in pre-`1.0.0` development, and most of its public
API already keeps strict backward compatibility
([Versioning and compatibility](https://lightine.youtrack.cloud/articles/TES-A-8)), so
contribution discipline matters:

- **Kotlin, JVM, and Android APIs:** strict. No breaking change within `0.x`.
- **`TesseraUI`** (the hand-written Swift scanner screen): strict. No breaking change
  within `0.x`. The API baseline check in tessera-swift CI guards it.
- **The Swift form of the `Tessera` framework** (generated by Kotlin/Native from the
  Kotlin API): may change before `1.0.0`, so its rough edges can be fixed (crashing
  calls, values typed as `Any`, mangled names). Every such change gets its own line under
  a "Swift" heading in `CHANGELOG.md`, with what to change in calling code.

This file is a short pointer. The full contributor reference is the Contribute section of
the public documentation, which lives in the project's public knowledge base, not in this
repository.

## Where you fit

Not sure which tasks you can take on your machine, or which page to read first?
[Contribute to Tessera](https://lightine.youtrack.cloud/articles/TES-A-78) is the way in:
it lists every contributor page. The one hard constraint: iOS work needs macOS.

## First-time setup

Start with [Set up a machine to build Tessera](https://lightine.youtrack.cloud/articles/TES-A-12).
You don't need to sign your own commits: branch protection requires signatures only on
commits that land on `main`, and the squash merge commit GitHub makes for your PR is
signed by GitHub. Release tags are signed by the maintainer.

## Before you open a PR

1. **Branch off `main`** with `feature/`, `fix/`, `docs/`, or `chore/` and a short
   description. CI rejects other names.
2. **Check the open GitHub issues** for work in progress and settled decisions.
3. **Run the local checks:** `./gradlew check` (compile, tests, Spotless, ktlint) and
   `python3 -I scripts/check-docs.py pointers`.
4. **Fill in the PR template** at
   [`.github/pull_request_template.md`](.github/pull_request_template.md), including the
   feature documentation checklist when you add or change public API. Public
   documentation pages are knowledge base pages, not repo files: link or attach your
   draft pages and the maintainer publishes them at the release.
5. **Update `CHANGELOG.md`** under `[Unreleased]`
   ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/)), or ask for the
   `no-changelog` label when nothing ships.

## Review

Every PR to `main` must pass the required checks before it can merge; branch protection
enforces that. [`.github/CODEOWNERS`](.github/CODEOWNERS) names the maintainer, who
reviews and merges. Code-owner approval becomes a requirement when the project has a
second maintainer.

## Reporting issues

- **Bug or feature request:** open a GitHub issue.
- **Security vulnerability:** follow [`SECURITY.md`](SECURITY.md). Do not open a public
  issue for a security report.

## Significant changes: discuss first

Open an issue before you change:

- the public API of any module;
- the error types (`MrzError`, `MrzValidationError`, `MrzWarning`);
- an architectural decision (the maintainer keeps the decision records);
- cross-cutting concerns (I/O posture, telemetry, scope).

API changes are expensive under strict backward compatibility, and small misalignments
compound. The earlier the conversation, the cheaper the change.

## Code of conduct

Be kind, be specific, assume good faith. A formal code of conduct may follow if the
contributor base grows beyond a small team.
