- **`Tessera` XCFramework + Swift Package Manager packaging for iOS** (the `0.2.0` iOS SPM slice; [ADR-019](docs/decisions/0019-ios-distribution-via-spm.md)). The `mrz-camera-ios` module becomes the **iOS distribution umbrella**: its `build.gradle.kts` declares a static framework binary on each iOS target and an `XCFramework("Tessera")` that bundles both slices (`iosArm64` device + `iosSimulatorArm64` simulator) into one `Tessera.xcframework` via `assembleTesseraXCFramework`. Explicit exports are used in place of the experimental `transitiveExport` (which also drags coroutines' internal `atomicfu` interop into the export); `isStatic = true` keeps the SPM `binaryTarget` sign-free for consumers. A new `packTesseraXCFramework` Gradle task assembles the release framework and zips it to `build/distributions/Tessera.xcframework.zip` — the artifact an SPM `binaryTarget(url:checksum:)` consumes — so the full assemble → zip pipeline is reproducible ahead of the release (verified end-to-end: a 7.1 MB zip with a valid `swift package compute-checksum`). The `ios-compile` CI job now also runs `assembleTesseraDebugXCFramework`, so a broken `export(...)` surface fails CI rather than the release. **Resolved** the `Package.swift`-location sub-decision left open by ADR-019: a **dedicated distribution repo** (planned `lightine-io/tessera-swift`) per JetBrains' KMP guidance, fixing a stable iOS consumption URL from the first iOS release. Only `mrz-camera-ios` is off Maven Central — iOS ships through SPM (the camera core/Android modules' Maven publishing is wired in its own entry above). **Deferred to the `0.2.0` release cut:** creating the distribution repo, attaching the zip to the GitHub release, and finalizing `Package.swift`. No code or public-API change to the modules themselves. - **`AVCaptureMrzScanner` — the iOS owns-the-camera-session scanner** (the `0.2.0` iOS camera slice, the iOS analogue of Android's `CameraXMrzScanner`, on the shared `mrz-camera-core` contract). A new `iosMain` `MrzCameraScanner` + `AutoCloseable` in `mrz-camera-ios` that runs an `AVCaptureSession` internally so the consumer never touches AVFoundation: it adds an `AVCaptureVideoDataOutput` with `alwaysDiscardsLateVideoFrames = true` (the iOS counterpart of CameraX's `STRATEGY_KEEP_ONLY_LATEST`), bridges the delegate's `CMSampleBuffer`s into the existing frame-source-agnostic `scan(frames, releaseFrame, captureErrorFor)` engine, and streams one `MrzScanResult` per analysed frame on `results`. Permission is read-only — `AVCaptureDevice.authorizationStatus(for:)` (which never prompts), reported as `CameraError.PermissionDenied` when not authorized; the scanner never calls `requestAccess…` (`scope.md` "permission boundary"). No camera for the requested position is `CameraUnavailable`; asynchronous failures arrive as `AVCaptureSession` notifications — an interruption with reason `videoDeviceInUseByAnotherClient` maps to `CameraError.CameraInUse`, a session runtime error to `CameraUnavailable` — surfaced on `results` as a `MrzScanResult.CaptureError`, never thrown (mirroring Android's async camera-state surfacing). **The genuinely-new iOS concern — `CMSampleBuffer` lifetime** — is handled by taking explicit ownership: because a `CMSampleBuffer` is a Core Foundation type Kotlin/Native's ARC does not manage, the capture delegate `CFRetain`s each buffer before handing it across the coroutine boundary and it is `CFRelease`d exactly once (by `scan`'s `releaseFrame` after analysis, or by the frame channel's `onUndeliveredElement` when a newer frame supersedes it or the session tears down) — the retain/release counterpart of Android's mandatory `ImageProxy::close`. Back-pressure deliberately differs from Android: rather than blocking AVFoundation's serial sample-buffer queue (which Apple's guidance forbids), the delegate does a non-blocking send into a capacity-1 `DROP_OLDEST` channel, so the newest frame always wins and stale frames are released rather than analysed — the same "only the latest frame" intent reached without blocking capture. Uses only Kotlin/Native platform libraries (`platform.AVFoundation` / `platform.CoreMedia` / `platform.CoreFoundation` / `platform.darwin`) plus the coroutines already on the core's public API — no external dependencies. Verified: compiled for both iOS targets (`iosArm64` / `iosSimulatorArm64`) on the `ios-compile` CI job, with the module's simulator test suite still green. The `MrzCameraScanner` contract and the `scan` engine this builds on are host-tested in `mrz-camera-core`; the live-camera behaviour — frame streaming, the `CMSampleBuffer` retain/release accounting under load, and the async in-use / runtime-error mapping — is device-verified separately because the iOS Simulator has no camera, exactly as the Android scanner's CameraX wiring was device-verified after it shipped. The `CameraInUse` live scenario (another client holding the camera) is the same not-yet-device-exercised gap recorded for Android (see [`docs/open-questions.md`](docs/open-questions.md)). The module remains unpublished this slice (iOS distribution is an XCFramework → Swift package, [ADR-019](docs/decisions/0019-ios-distribution-via-spm.md), built at the release slice). Doc-sync landed with the slice: `docs/features/mrz-camera-reading.md` (status table + the iOS owns-session example and error-surfacing paragraph), `docs/features/mrz-error-taxonomy.md` (the iOS failure-to-member mapping), `docs/reading-risks.md` (the `CMSampleBuffer` memory-hygiene discipline), `docs/architecture.md` (`AVCaptureMrzScanner` now present, no longer "a following slice"), `docs/open-questions.md` (the `CameraInUse` entry retitled to span Android + iOS), and `docs/testing.md` (the owns-the-camera-session scanners are compile-checked on CI and device-verified, not host-tested).
- **`mrz-camera-ios` module — the iOS Apple Vision OCR seam (`VisionMrzTextRecognizer`)** (the `0.2.0` iOS camera slice, mirroring Android's analyse-frame recognizer on the shared `mrz-camera-core` contract). A new iOS-only Kotlin Multiplatform module (`iosArm64`/`iosSimulatorArm64`; no Android Gradle plugin) that implements `MrzTextRecognizer<CMSampleBufferRef>` — binding the analyse-frame core's frame type to the `CMSampleBuffer` an `AVCaptureVideoDataOutput` delivers, exactly as Android binds `F = ImageProxy`. `recognize()` extracts the pixel buffer (`CMSampleBufferGetImageBuffer`), runs a Vision `VNRecognizeTextRequest` (`recognitionLevel = .accurate`, **`usesLanguageCorrection = false`** — the MRZ is not natural language, so language correction would *change* characters, which reader-not-oracle forbids) via `VNImageRequestHandler`, and maps `VNRecognizedTextObservation.topCandidates(1)` into `RecognizedText`, ordering observations top-to-bottom (Vision does not guarantee reading order) so the analyzer sees the MRZ lines in document order. A Vision failure throws and surfaces as `CameraError.OcrFailed`, with recognized text kept out of the message (PII). The module uses only Kotlin/Native platform libraries (`platform.Vision` / `platform.CoreMedia` / `platform.CoreVideo`) — no external dependencies, unlike Android's CameraX/ML Kit. It depends on `mrz-camera-core` and is unpublished this slice (iOS distribution is an XCFramework → Swift package, [ADR-019](docs/decisions/0019-ios-distribution-via-spm.md), built at the release slice). Verified: compiled for both iOS targets on the `ios-compile` CI job, and a simulator test drives the Vision pipeline end-to-end on `iosSimulatorArm64` (handler → request config → `performRequests` → result reading → ordering, asserting a blank image yields no lines). On-device / real-MRZ OCR accuracy — subject to the same OCR-brittleness caveat the Android slice recorded — is verified with the owns-the-camera-session `AVCaptureMrzScanner` in the following slice.

### Changed

- **Owns-the-camera-session iOS scanner (`AVCaptureMrzScanner`) now surfaces a camera-in-use interruption as a non-terminal observation and lets AVFoundation auto-resume — mirroring the Android recoverable-in-use contract** (the iOS half of the `CameraInUse` live-verification slice, completing full cross-platform symmetry before [ADR-007](docs/decisions/0007-strict-backward-compat-from-0x.md) locks it at the `0.2.0` tag). An `AVCaptureSession` interruption with reason `videoDeviceInUseByAnotherClient` previously closed the frame channel — a *terminal* `CameraInUse`. It is now surfaced as a **non-terminal** `MrzScanResult.CaptureError(CameraInUse)` emitted onto `results` while the session stays bound, so AVFoundation's `AVCaptureSessionInterruptionEnded` auto-resumes capture when the other client releases the camera — the same recovery the backgrounding interruption already used (only a session *runtime error*, a genuine media-services fault, stays terminal). The now-unused `CameraInUseException` close path is removed, and the recoverable-reason decision is factored into a pure `isVideoDeviceInUseReason(reason)` so it is host-tested in `iosTest` (replacing the in-use exception-mapping case — the iOS counterpart of Android's `classifyCameraState` test; four `iosTest` cases). **Device-verified** on a physical iPhone (iPhone 15 Pro / iOS 26.5): a real reason-3 interruption was staged via **Continuity Camera** (the Mac borrowing the iPhone's lens — app-switching and Continuity otherwise yield to the foreground app, so a Mac-side grab is what produces a genuine `videoDeviceInUseByAnotherClient` against a running session), and the scanner surfaced `CaptureError(camera.in_use)` while frames kept flowing, then resumed on `InterruptionEnded` — reproduced twice, the stream never completing. This **resolves the iOS half** (and with it the whole `CameraInUse` live-verification open question): both platforms now treat a recoverable in-use as non-terminal-and-recovering. No public-API-signature change — the `results` contract for an iOS in-use changes from terminal to non-terminal-and-recovering, matching Android. Doc-sync: `docs/open-questions.md` (iOS half resolved; the entry is now Resolved) and the `AVCaptureMrzScanner` KDoc verification-status note.
- **Owns-the-camera-session Android scanner (`CameraXMrzScanner`) now surfaces a *recoverable* camera-in-use as a non-terminal observation and lets CameraX auto-recover, instead of ending the scan** (the Android `CameraInUse` live-verification slice — finishing the camera-error contract before [ADR-007](docs/decisions/0007-strict-backward-compat-from-0x.md) locks it at the `0.2.0` tag). CameraX classifies its `CameraState` errors as *critical* (no auto-recovery — permission / fatal hardware / camera removed) or *recoverable* (`ERROR_CAMERA_IN_USE`, `ERROR_MAX_CAMERAS_IN_USE`, `ERROR_OTHER_RECOVERABLE_ERROR` — CameraX keeps retrying, parking the camera in `PENDING_OPEN` until the blocker clears). The scanner previously closed the `results` stream on **any** state error, which for a recoverable code tore down a session CameraX would have recovered — premature, and an oracle-ish "this session is over" decision on a transient condition. It now ends the session only on a **critical** error; a **recoverable** one is emitted as a *non-terminal* `MrzScanResult.CaptureError` (`CameraInUse` for the two in-use codes, `CameraUnavailable` for other-recoverable) while the session stays bound, so CameraX resumes streaming once the camera is free (reader-not-oracle: report the in-use observation, do not decide it ends the session). The recoverable/critical decision is extracted into a pure `classifyCameraState(code, hasCameraPermission)` function. **Locked by `mrz-camera-android`'s first host tests** — a new `androidHostTest` source set (`withHostTest {}`; the Android counterpart of `mrz-camera-ios`'s `AVCaptureMrzScannerErrorMappingTest`, and the module's first host tests since the contract moved to `mrz-camera-core`), six tests asserting the recoverable-vs-terminal decision and the permission-collapse mapping across all eight `CameraState` codes, now run by the `android-compile` CI job. **Device-verified** on a physical device (Galaxy S24, API 36): a second camera client grabbing the lens makes CameraX report `ERROR_CAMERA_IN_USE` (state error 2 — recoverable), which the scanner surfaces as a non-terminal `CaptureError(camera.in_use)` and then **resumes streaming** when the lens is released — reproduced across runs, with the stream never terminating and exactly one in-use event emitted per occurrence (a dedup latch suppresses repeats while parked). This **resolves the Android half** of the `CameraInUse` live-verification open question and confirms `ERROR_CAMERA_IN_USE` is the recoverable code Android actually reports. The iOS scanner gets the same non-terminal recovery in the companion *Changed* entry above (full cross-platform symmetry). No public-API-signature change — what changes is the `results` contract for a recoverable in-use: terminal-then-dead becomes non-terminal-and-recovering. ### Fixed

- **Owns-the-camera-session iOS scanner (`AVCaptureMrzScanner`) no longer stalls after a few seconds of live capture** (the iOS live-device test). On device, capture would stop delivering frames after a few seconds — session still running, no interruption, no dropped-frame callbacks — and the `results` stream went silent. Root cause: `AVCaptureVideoDataOutput` holds its sample-buffer delegate **weakly** (Cocoa convention), and Kotlin/Native reclaims bridged Objective-C objects by **garbage collection, not ARC** — so the inline-created delegate, with no strong Kotlin reference, was collected on the next GC pass, leaving the output's weak pointer `nil`. The stall scaled with per-frame allocation (more memory → GC sooner → delegate collected sooner), which made it masquerade as a buffer-pool/memory problem. Fix: `AVCaptureMrzScanner` holds the delegate in a field for the session's lifetime. Two supporting changes keep Vision off the finite capture pool and bound memory: `VisionMrzTextRecognizer` runs Vision on an independent, reused heap copy of each frame (row-by-row stride-correct copy, per Apple's "copy if you hold the buffer beyond the delegate callback" guidance) rather than the camera buffer, and the scanner analyses at most ~5 frames/sec (the "don't OCR every frame" practice) with a single reused `VNRecognizeTextRequest`. Device-verified on iPhone 15 Pro / iOS 26.5: 770 analysed frames with zero freezes and zero dropped frames, memory a bounded ~96–253 MB sawtooth (Kotlin/Native's automatic GC reclaiming Vision's native allocations — no forced GC needed), and live `MrzScanResult.Decoded` (`ParseResult.Success`) read from a real document. This also closes the previously-unverified live `Decoded`-from-camera gap on iOS. The Kotlin/Native weak-delegate pitfall is recorded in [`.claude/known-pitfalls.md`](.claude/known-pitfalls.md); details in [`docs/open-questions.md`](docs/open-questions.md).
- **Owns-the-camera-session Android scanner (`CameraXMrzScanner`) now surfaces a typed `CaptureError` when the camera fails to open, instead of going silent** (the fifth `0.2.0` slice — the Android live-device test). The device run found that CameraX reports a failed open (permission denied, hardware fault) **asynchronously through camera state**, not as a `bindToLifecycle` exception — so the previous code, which only mapped a (never-thrown) synchronous `SecurityException`, left the `callbackFlow` open with no frames and no error, and the consumer's `results` stream went silent. The scanner now observes `CameraState` and routes a state error through `scan()`'s catch path as a `MrzScanResult.CaptureError`. The error code maps to `CameraInUse` (in-use / max-cameras) or `CameraUnavailable`; because CameraX collapses a *permission* denial into a generic `ERROR_CAMERA_FATAL_ERROR` with no cause (its public state API does not distinguish "no permission" from a hardware fault), the scanner reads the observable `CAMERA` permission state — read-only, never requesting it — to report `PermissionDenied` when that is the actionable cause (reader-not-oracle: report the observable fact, do not infer an unobservable cause). Device-verified on a physical device: `PermissionDenied` on a revoked permission, clean streaming with no spurious error when granted. The `CameraInUse` code-mapping is in place; its live in-use behaviour was device-exercised in the later `CameraInUse` live-verification slice (see the *Changed* entry on the recoverable-in-use contract), which also revised it from terminal to non-terminal-and-recovering.
- **Camera telemetry now honours `TelemetrySinkRegistry`** (pre-`0.2.0`-tag fix). The frame analyzer (`MrzFrameAnalyzer`) and both owns-session scanners (`CameraXMrzScanner`, `AVCaptureMrzScanner`) defaulted their `telemetry` parameter to `NoOpTelemetrySink`, so a consumer who followed the documented contract — `TelemetrySinkRegistry.register(sink)` at startup — received **no** camera events: the scanner silently used the no-op and ignored the registry, even though `telemetry.md` and [ADR-015](docs/decisions/0015-telemetry-contract-only-at-0-1-0.md) state that emitters read `TelemetrySinkRegistry.current`. The default is now `TelemetrySinkRegistry.current` (captured at construction), so startup registration reaches the camera as documented; an explicit `telemetry` argument still overrides per instance, and with nothing registered events route to `NoOpTelemetrySink` as before. Surfaced while backfilling feature usage examples (action-plan B5) and fixed before the `0.2.0` tag locks the contract under [ADR-007](docs/decisions/0007-strict-backward-compat-from-0x.md). Host-tested in `mrz-camera-core`.

### Removed

- The `TestInfrastructureSmokeTest` placeholder in `mrz-core` (replaced by real tests as implementation slices landed)

- `MrzGenerationMissingRequiredField` error type — removed pre-tag during the 2026-05-19 full alignment audit (Phase D, test-coverage discipline). The type was defined as a public sealed subtype of `MrzGenerationError` but had no production path: every required parameter on the primitive-input generator methods is non-nullable in Kotlin, and the data-model-input methods take fully-constructed `MrzDocument` instances whose `CommonFields` are all non-nullable too. Kotlin's type system enforces required-field presence at compile time, so no runtime code path could emit this error, and no test produced it. Under [ADR-007](docs/decisions/0007-strict-backward-compat-from-0x.md)'s strict-backcompat rule, keeping the type would have locked it into the API forever; removing pre-tag is the cheap correction. If a future generator API takes Map-like input where required fields can be omitted at runtime, the type can be re-added then
