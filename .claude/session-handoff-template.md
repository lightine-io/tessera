# Session Handoff Template

A handoff is how one Claude Code session transfers state to the next. Claude Code reads the project from scratch each session; without an explicit handoff, context fades and progress gets rebuilt from inference rather than knowledge.

**Write it for its actual reader: the next AI session.** AI-first does not mean machine-format — prose is fine, and it carries reasoning and caveats better than rigid fields. It means:

- **Deterministic structure.** Always the same sections, always in this order, so nothing is missed.
- **State first, history second.** The reader needs "where are we and what's next" before "what happened."
- **Exact references, not re-explanation.** Commit hashes, PR numbers, `file:line`, exact commands. Point at committed docs instead of paraphrasing them — a paraphrase can drift; a pointer cannot.
- **Explicit status vocabulary.** `DONE` / `IN-FLIGHT` / `PARKED` / `BLOCKED(on …)` — never narrative "mostly finished."
- **Filled by looking, not remembering.** The Standing Obligations section in particular is generated by running the sweep, not from working memory. A handoff written purely from memory inherits the session's blind spots — that is the failure mode this template exists to prevent.
- **Lean.** Every line costs the next session context budget. Link out; do not duplicate what committed docs already say. Soft cap ~120 lines.

---

## When to Use It

At the end of any session that made non-trivial progress, stopped mid-task, made decisions affecting future work, hit surprises that change the path, or touched the project's issue tracker. Trivial sessions (a small fix, a one-question consultation) do not need one.

## Where to Put It

A file in `.handoffs/`, named:

```
SESSION-HANDOFF-YYYY-MM-DD-HHMM-<slug>.md
```

- `YYYY-MM-DD` — UTC date; `HHMM` — UTC time, four digits, no separator (`date -u +%H%M`).
- `<slug>` — short kebab-case summary of what the session shipped; match the feature branch's slug when there is one.

Both time and slug are mandatory: the time makes `ls -1 .handoffs/SESSION-HANDOFF-*.md | sort -r | head -1` deterministic (no mtime dependency); the slug makes the listing self-documenting. Older files may use legacy forms (date-only, or date+slug); treat them the same when reading, do not bulk-rename.

**Never commit handoff files** — `.handoffs/` is gitignored working notes.

---

## Status vocabulary

Handoffs tag every work item with one of these four words. Their meaning is fixed
here, so a handoff just uses the word — it does not re-explain it.

- **DONE** — finished and verified; nothing left on this thread. Carries its exact
  reference (PR #, commit, `file:line`).
- **IN-FLIGHT** — actively in progress: partly built, with one concrete next action
  named.
- **PARKED** — deliberately paused, *not* dropped. The work is still intended; it is
  waiting on something — a decision, a required order ("do X first"), or a chosen
  slower pace. A PARKED item must always say two things: **what un-parks it**, and
  **what it means for the next session** (e.g. "continue, but one slice at a time —
  do not do it all at once").
  - **Separate the approach from the rollout.** The *approach* (the plan or idea) can
    be alive while the *rollout* (executing it) is the part that's paused. A parked
    rollout is **not** a dropped approach — say which one is parked, or the next
    session will read "we paused the work" as "we abandoned the plan." (This exact
    mix-up has happened — see [`known-pitfalls.md`](known-pitfalls.md).)
- **BLOCKED(on …)** — cannot move until the named thing resolves (an external
  dependency, an unanswered question, a pending merge). Always name the blocker in
  the parentheses.

## The Template

```markdown
# Session Handoff — YYYY-MM-DD HHMM UTC (<slug>)

Supersedes: <previous handoff filename, when this one replaces a same-arc handoff; omit otherwise.
When present, START HERE must restate the whole current plan, not just the delta — see below.>

## ⭐ START HERE

[The state snapshot, 3–6 bullets. Lead with the plan and where it stands — what we're doing
and the open threads by name, each with a one-line status — then version, `main` commit, and
branch/working-tree state (clean/dirty). Put cautions LAST, never first: a stack of "don't"
at the top of START HERE gets read as the headline. This is the section the next session acts
on; everything below is supporting detail.

**One exception** — a single *"this looks broken but it's intentional"* orientation note may
lead, but only when the most likely fresh-session mistake is *undoing finished work* (e.g.
restoring a folder that was deleted on purpose). This is not a "don't" caution; it stops the
reader from reversing completed work before they reach the plan. Keep it to one short block;
everything else still goes last.

If a `Supersedes:` line is present, the next session never saw the superseded handoff — so
restate the WHOLE current plan here, affirmatively (what we're doing, why, where it stands,
how it proceeds), not just what changed. The delta goes in "Superseded This Session"; the
state goes here. (See known-pitfalls.md "Writing a Correcting Handoff as a Diff Instead of a
Fresh Statement.")]

## What This Session Did

[DONE items only, each with its exact reference (PR #, commit, file path). Brief.]

## Decisions Made

[Decisions affecting future work, with one-line reasoning and a pointer to where each
was recorded (ADR, issue-tracker entry, plan). A decision recorded only here is at
risk — graduate it.]

## What Is in Flight

[Partially-done work, each tagged IN-FLIGHT / BLOCKED(on …) / PARKED, with the exact
file/branch and the next concrete action. "Nothing" is a valid value — but only after
the Standing Obligations sweep below confirms it.]

## Standing Obligations (swept, not remembered)

[MANDATORY, generated by looking. Three beats, in order:
1. `grep -n '\- \[ \]' .plans/*.md` — local plan checkboxes (usually empty; the backlog
   of record is YouTrack).
2. YouTrack sweep (when active): `search_issues` with query `project: TES #Unresolved`,
   scan the hits for Trigger/un-park lines, and list every trigger that fired this
   session (a tag pushed, a release shipped, a date crossed, an external reply). If
   YouTrack is dormant, write "YouTrack sweep: SKIPPED (dormant)" — never silently omit
   the beat.
3. CLAUDE.md cadence dates — note crossed / not crossed.
If the sweep output contradicts "What Is in Flight", the sweep wins.]

## Superseded This Session

[Facts that stopped being true this session — "X is no longer the case; now Y" — with
a pointer to where the new truth is recorded. This is how stale knowledge gets
retired instead of resurfacing later. Omit only if genuinely nothing changed.]

## Surprises / Lessons

[Unexpected findings, each with where it was recorded (known-pitfalls, working-patterns,
an ADR, a YouTrack issue). The lesson's home is a committed or tracked place; this list
is just the pointer. A surprise with no home yet does NOT ship in the handoff alone —
record it or file an issue first, then point at it. Handoffs get archived; anything
living only here dies with them.]

## Next Session Should

[Numbered, specific, actionable — "do X by doing Y", never "continue the project."
Item 1 is the default starting move.]

## Things to Watch For

[Specific cautions: things that look true but aren't, files that bite, dead tags,
flaky tests. Include the negative space — what NOT to do.]

## Open Questions Touched

[the project's issue tracker entries modified / resolved / added, by title. "None" is valid.]
```

## Example (abbreviated, fictional)

```markdown
# Session Handoff — 2026-05-15 2210 UTC (td3-parser)

## ⭐ START HERE

- `main` at `abc1234`, version 0.1.0-dev, working tree clean, branch `feature/td3-parser` merged (#25).
- One thread open: TD3 long-document-number extension — IN-FLIGHT, see below.

## What This Session Did

- TD3 parser incl. check digits (#25, `mrz-core/.../Td3Parser.kt`), 47 tests passing.

## What Is in Flight

- IN-FLIGHT: long-doc-number composite digit — TODO at `Td3Parser.kt:142`, test written
  but `@Ignore`d (`Td3ParserLongDocNumberTest.kt`). Next action: implement, un-ignore.

## Standing Obligations (swept, not remembered)

- `.plans/ACTION-PLAN-….md`: `- [ ] [P4] Android integration guide` (unchanged, not this arc).
- No issue-tracker triggers fired this session.

## Superseded This Session

- "TD3 parsing is unimplemented" — no longer true; parser shipped in #25. Feature doc
  Status section updated.

## Next Session Should

1. Implement the long-doc-number extension at `Td3Parser.kt:142`; remove the `@Ignore`.
```

## Maintaining This Template

The template evolves: drop sections that consistently go unused, add ones consistently needed. Keep the AI-first properties above intact — they are the design, not decoration. The companion enforcement lives in `scripts/standing-obligations.sh` (SessionStart hook: injects START HERE + Next Session Should + Things to Watch For from the latest handoff, with a staleness warning when commits postdate it), `scripts/stop-handoff-check.sh` (Stop hook: handoff reminder for substantive sessions — git commits or YouTrack writes, the latter flagged by `scripts/mark-substantive.sh`), and CLAUDE.md "What to Do First" step 2. The three injected section headings (⭐ START HERE, Next Session Should, Things to Watch For) are matched by name in the banner script's awk pattern — renaming any of them requires updating `scripts/standing-obligations.sh` and its test in the same change.
